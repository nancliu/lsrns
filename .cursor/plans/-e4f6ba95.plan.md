# 批次监控层级组织与结果分析改进提案

**Change ID**: `batch-monitoring-hierarchy-and-results-analysis`

**Status**: 📋 Proposal (Planning)

**Priority**: Medium (P1 - UX and functionality improvement)

**Created**: 2025-11-02

---

## Executive Summary

改进批次监控功能，将批次列表从平级展示改为按Case分组的层级结构，实现两层结果分析体系：第一层基于summary.xml提供快速概览对比，第二层详细分析（基于tripinfo.xml和edgedata.xml）作为后续迭代。同时确保同一批次内所有仿真的输出配置完全一致，以保证对比分析的公平性和准确性。

**核心改进点**：

1. 批次列表按Case分组展示（Case → Batches层级结构）
2. 两层结果分析体系：快速概览（summary.xml）+ 详细分析（后续迭代）
3. 同一批次输出配置统一（用户选择输出级别，应用于所有方案）
4. 基准方案强制要求（每个批次必须包含1个baseline_plan）
5. 随机仿真次数可配置（1-10次，用户选择）

---

## Problem Statement

### 当前问题

**批次列表组织问题**：

- 当前批次列表平级展示所有批次，不反映实际的层级结构（cases → case → batch）
- 同一Case下的多次批量仿真混在一起，难以按Case查找
- 缺少Case级别的汇总信息（如：case_001下有多少批次，最新批次是什么）

**结果分析缺失**：

- 当前只有简单的峰值曲线展示
- 缺少方案间的对比分析（基准方案 vs 管控方案）
- 无法快速评估管控策略的效果（改善率、通行能力提升等）

**输出配置不一致风险**：

- 如果同一批次内不同方案的输出配置不同，对比结果会失真
- 例如：baseline使用完整模式（有tripinfo），管控方案使用精简模式（无tripinfo），无法公平对比

**基准方案管理问题**：

- 基准方案的必需性未明确
- 用户可能忘记创建基准方案，导致无法对比

## Proposed Solution

### 1. 批次列表层级组织

**UI结构**：

```
批次监控视图
├─ 📁 Case分组A (case_001 - 案例名称)
│   ├─ batch_20251101_140530
│   │   ├─ 状态：已完成 ✓
│   │   ├─ 方案数：4个（1个基准 + 3个管控）
│   │   ├─ 任务数：12个（4方案 × 3次随机）
│   │   └─ 创建时间：2小时前
│   └─ batch_20251102_091500
│       ├─ 状态：运行中 ⏳
│       ├─ 方案数：3个（1个基准 + 2个管控）
│       └─ 任务数：9个（3方案 × 3次随机）
│
└─ 📁 Case分组B (case_002 - 案例名称)
    └─ batch_20251102_153000
        └─ ...
```

**交互设计**：

- Case分组可折叠/展开（默认展开）
- 每个分组显示汇总信息：批次数量、最新批次状态
- 批次卡片显示在对应Case分组下
- 筛选和排序在Case级别内生效（不影响跨Case）

**实现要点**：

- 前端按case_id分组渲染批次列表
- 保持现有的批次卡片样式和功能
- 分组头显示：Case ID、案例名称、批次计数、最新批次时间

### 2. 两层结果分析体系

#### 第一层：快速概览（基于summary.xml）

**数据来源**：

- 每个仿真任务的结果目录：`cases/{case_id}/simulations/plan_opti/{batch_id}/{plan_id}/sim_{seed}/summary.xml`
- 解析summary.xml的最终step元素获取汇总指标

**展示内容**：

**对比表格**：

| 方案 | 平均旅行时间 | 改善率 | 通行能力 | 改善率 | 平均等待时间 | 改善率 | 最高在网车辆 |

|------|------------|--------|---------|--------|------------|--------|------------|

| baseline | 1201.67s | - | 28666辆 | - | 180.5s | - | 8520辆 |

| plan_001 | 1051.67s | +12.5% ↑ | 29500辆 | +2.9% ↑ | 150.3s | +16.7% ↑ | 8120辆 |

| plan_002 | 1100.20s | +8.4% ↑ | 29200辆 | +1.9% ↑ | 160.8s | +10.9% ↑ | 8240辆 |

**统计逻辑**：

1. 对每个方案的N次随机仿真取平均值（去除异常值）
2. 使用baseline的平均值作为基准线
3. 计算管控方案相对baseline的改善率：

   - 改善率 = (baseline值 - 管控方案值) / baseline值 × 100%
   - 正值表示改善（↑），负值表示恶化（↓）

**可视化**：

- 柱状图对比（各方案的指标对比）
- 改善率雷达图（可选，展示多维度改善效果）
- 峰值在网车辆曲线对比（所有方案的曲线叠加）

**UI位置**：

- "结果"标签页的默认视图
- 点击批次卡片的"查看结果"按钮跳转到此视图

---

#### 第二层：详细分析（后续迭代）

**数据来源**：

- `tripinfo.xml`：车辆级别详细数据
- `edgedata.xml`：路段级别聚合数据（如果启用）

**潜在分析内容**（待用户反馈后确定）：

- 车辆级别时间分布直方图
- 路段级别速度/流量热力图
- 管控策略影响区域前后对比
- 时间序列曲线（速度/流量随时间变化）
- 换道行为分析（DHS策略效果）

**实施策略**：

- 先完成第一层分析
- 收集用户反馈后决定第二层的具体功能
- 如需实施，按需加载数据（不预先加载大文件）

### 3. 批次配置一致性保证

**设计原则**：

> **同一批次内所有仿真的输出配置必须完全相同**，这是进行公平对比的基础。

**配置参数**：

用户在创建批次时选择输出级别（应用于所有方案，包括baseline）：

```json
{
  "output_level": "minimal" | "standard" | "full",
  "num_seeds": 1-10,  // 每个方案的随机仿真次数
  "base_seed": 66     // 起始种子值
}
```

**输出级别定义**：

| 级别 | summary.xml | tripinfo.xml | edgedata.xml | E1检测器 | 适用场景 |

|------|------------|-------------|--------------|---------|---------|

| **minimal** | ✅ 必需 | ❌ 禁用 | ✅ 仅管控区域 | ❌ 禁用 | 批量快速筛选 |

| **standard** | ✅ 必需 | ✅ 启用 | ✅ 全路网 | ✅ 管控区域 | 详细评估 |

| **full** | ✅ 必需 | ✅ 启用 | ✅ 全路网 | ✅ 全量龙门架 | 研究/演示 |

**实施要点**：

- 批次创建时保存`simulation_config.json`到批次目录
- 每个任务执行时读取此配置，应用相同的输出设置
- 配置验证：确保所有方案的输出配置一致

---

### 4. 基准方案强制要求

**规则**：

- 每个批次创建时，系统自动确保包含baseline_plan
- 如果用户未选择baseline_plan，系统自动添加
- baseline_plan在方案列表中标记为"基准方案"（不可删除）

**批次组成**：

```
批次batch_001：
├─ baseline_plan (基准方案) ← 系统强制包含，1个
└─ plan_001, plan_002, ... (管控方案) ← 用户选择，0或多个
```

**随机仿真处理**：

- baseline_plan同样执行N次随机仿真（seed=66,67,68,...）
- 所有方案使用相同的seed序列，便于交叉对比

---

### 5. 随机仿真次数配置

**用户配置**：

- 创建批次时，用户可选择每个方案的随机仿真次数（1-10次）
- 默认值：3次
- 所有方案（包括baseline）使用相同的次数

**种子分配规则**：

- 如果num_seeds=3, base_seed=66
- 所有方案的seed序列：66, 67, 68
- 不同方案的同一轮次使用相同seed（便于对比）
- 同一方案的不同轮次使用不同seed（增加随机性）

## Design Decisions

### 为什么按Case分组而不是其他维度？

**理由**：

- 符合实际的数据结构（cases → case → batch）
- 用户通常按Case组织和管理仿真任务
- 便于查看同一Case下的历史批次

**替代方案已考虑但拒绝**：

- 按时间分组（本周/本月）：信息密度低，不直观
- 按标签分组：需要用户手动打标签，增加操作负担

### 为什么第一层分析只基于summary.xml？

**理由**：

- summary.xml文件小（~10-50KB），解析快速
- 包含核心对比指标（旅行时间、通行能力、等待时间）
- 不依赖大文件（tripinfo.xml ~200MB），加载速度快

**后续扩展**：

- 如果用户需要更详细的分析，可以通过第二层实现
- 避免过度设计，先满足核心需求

### 为什么同一批次必须统一输出配置？

**理由**：

- 对比分析的公平性要求：所有方案在相同条件下运行
- 避免配置差异导致的误判：
  - 例如：baseline有tripinfo可以计算车辆级别指标，管控方案无tripinfo只能看汇总指标，无法公平对比

### 为什么基准方案必须且只有1个？

**理由**：

- 对比分析需要一个明确的基准线
- 多个baseline会造成混乱（不知道以哪个为准）
- 简化逻辑：所有管控方案都与同一个baseline对比

## Data Flow

### 批次创建流程

```
用户创建批次
├─ 选择Case
├─ 选择管控方案（plan_001, plan_002, ...）
├─ 系统自动添加baseline_plan ← 强制
├─ 用户选择输出级别（minimal/standard/full） ← 应用于所有方案
├─ 用户选择随机次数（1-10，默认3）
└─ 保存批次配置
    └─ simulation_config.json → 应用于所有任务
```

### 结果分析流程

```
批次完成
├─ 读取所有方案的summary.xml
├─ 解析汇总指标（meanTravelTime, ended, meanWaitingTime等）
├─ 按方案分组聚合（N次随机仿真的平均值）
├─ 计算改善率（相对baseline）
└─ 渲染对比表格和图表
```

## Risks & Mitigation

| 风险 | 概率 | 影响 | 缓解措施 |

|------|------|------|---------|

| 同一批次内配置不一致导致对比失真 | 中 | 高 | 强制统一配置，批次创建时验证 |

| summary.xml解析失败 | 低 | 中 | 异常处理，返回错误信息，跳过该方案 |

| Case分组后批次列表过长 | 中 | 低 | 默认折叠已完成的Case分组 |

| 改善率计算错误 | 低 | 高 | 单元测试覆盖，验证计算公式 |

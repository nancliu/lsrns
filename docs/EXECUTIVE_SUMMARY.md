## 问题诊断

### 根本原因

用户点击"查看结果"时,前端需要调用progress API获取进度信息。该API在内部执行了非常昂贵的计算:

```
for each of 12-15 tasks:
  read summary.xml (几百KB文件)
  parse 5400+ XML step元素
  aggregate time series data

总耗时: 12 tasks × 1000-2000ms = 12-27秒
频率: 每1-2秒轮询一次
```

### 错误的设计

Progress轮询API原本被设计为同时返回:
- 进度信息 (实际需要)
- 时序数据 (实际不需要)

这导致高频操作(progress轮询)在计算低频才需要的数据。

---

## 解决方案

### 关键决策

分离progress API和results API的职责:

```
Progress API (高频, 每1-2秒)
  → 仅返回进度信息
  → 不计算时序数据
  → 响应时间: <100ms

Results API (低频, 用户点击时)
  → 返回完整结果
  → 包含时序数据
  → 响应时间: 3-5秒 (可接受)
```

### 实现

在 `api/services/batch_optimization_service.py` 的 `get_batch_progress()` 方法中:

```python
# 禁用计算复杂的时序聚合
live_time_series = {
    'time_points': [],  # 为空 (优化)
    'total_running': [],  # 为空 (优化)
    'task_count': len(progress_data["tasks"]),
    'last_update': datetime.now().isoformat(),
    'data_source': 'disabled_for_progress_optimization'
}

# vs 原来的:
# live_time_series = self._aggregate_live_time_series(...)  # 27秒!
```
